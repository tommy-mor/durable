# ramalite — durable + cljrs

*Like Rama, but the way sqlite is like Postgres: embedded, single-process,
zero infrastructure. The event log is a `.jsonl` file you can `grep`.*

This document is the research and design for pairing `durable` with
[cljrs](https://tytrdev.github.io/cljrs/), a Clojure dialect implemented from
scratch in Rust. The claim: durable is already Rama's single-node core, and a
Clojure VM hosted in the same process is the missing application layer that
would let it flourish.

## durable is already single-node Rama

Rama (Red Planet Labs) builds backends from four primitives. durable has all
four, minus distribution:

| Rama | durable | Notes |
|------|---------|-------|
| Depot (append-only distributed log) | `JsonlLog` / `Runtime::append` | fsynced JSONL tape, seq + monotonic ts stamped at ingest |
| ETL topology | `reducer: fn(&mut Tx, &E)` | one pure function; incremental == replay from zero |
| PState (indexed store of any shape) | RocksDB projection via `#[derive(Durable)]` schema | maps/lists/deques/sums, arbitrarily nested |
| Paths (Specter navigators) | typed `Path<S>` for writes, `Nav` algebra for reads | already serializable, already Specter-shaped |

Rama's own path language *is* Specter — a Clojure library. durable reinvented
its read algebra (`Field`/`Key`/`All`/`Where`/…) as closed data precisely so
that non-Rust clients could speak it. That decision is what makes a Clojure
frontend nearly free: EDN vectors of keywords and literals map 1:1 onto `Nav`.

What durable lacks is what Rama gets from being hosted in Clojure:
application code as data, a REPL against live state, and reducers you can
change without a compile-restart cycle.

## The cljrs landscape (August 2026)

Two active Clojure-on-Rust implementations exist; both confirm the pieces
ramalite needs:

- **[tytrdev/cljrs](https://tytrdev.github.io/cljrs/)** — reader, evaluator,
  macros, and persistent collections as a tree walker; type-hinted functions
  JIT to native code via MLIR/LLVM (`defn-native`, 2.4–13x faster than JVM
  Clojure on the benchmarks they publish); GPU kernels via WGSL. 61% of
  `clojure.core`, 100% of `clojure.string`/`set`/`walk`/`edn`.
  Two properties matter most here:
  - **Rust-crate interop via opaque handles** (rapier2d/3d already shipped
    this way) — exactly the shape `Runtime`/`Tx` need.
  - **Live redefinition without losing state** — their demo edits Conway's
    Game of Life rules mid-simulation. Swap "simulation" for "projection"
    and that is the ramalite development loop.
- **[csm/clojurust](https://github.com/csm/clojurust)** (`.cljrs` files,
  `cljrs` on crates.io) — tiered interpreter → IR → Cranelift JIT, AOT to
  native binaries, nREPL, and a documented embedding API
  (`cljrs-interop`: `Registry`, `NativeObject`, `FromValue`/`IntoValue`,
  `#[export]`). Proof that "embed a Clojure VM as the scripting layer of a
  Rust program" is a supported, not speculative, pattern.

## Why a Clojure VM completes durable

**1. The reducer becomes data, and the log makes that safe.**
Live-coding a stateful system is normally terrifying: redefine a function and
your in-memory state was built by code that no longer exists. Event sourcing
dissolves the problem — the projection is a pure function of the tape, so a
reducer edit is followed by `rebuild()` and the new world is *as if the new
code had always run*. durable already guarantees `incremental == replay from
zero` and ships `verify()`. cljrs already demonstrates hot redefinition
without losing the running system. Composed: edit reducer in the REPL →
replay → keep serving queries. That is a development loop neither Rust
(compile cycle) nor Python-over-IPC (can't hold the reducer) can offer.

**2. Reified writes mean the FFI boundary is data, not callbacks.**
durable mutations are already values (`Write` wrapping `Put`/`Delete`/
`DeletePrefix`/`Merge`). A cljrs reducer therefore doesn't need to call back
into the storage engine mid-transaction — it is a pure function from
`[meta event]` to a *vector of writes*, which the Rust side lowers and
commits atomically with the applied offset. Purity of reducers stops being a
convention and becomes the type of the interface.

**3. Paths-as-data is a Lisp idea; give it back its home syntax.**
`root.event_ids_by_kind().key(&e.kind).push_op(&e.id)` in Rust is
`(r/push [:event-ids-by-kind (:kind e)] (:id e))` in cljrs. The read algebra
is even better: `[:events (r/where (r/gt :epoch 4)) :kind]` is both the query
the human reads and the CBOR the engine executes. Schema declarations become
EDN instead of a derive macro, which means the schema can be inspected,
diffed, and generated by the same language that writes the reducers.

**4. Schema evolution = edit + replay, no migrations.**
durable's docs already say it: "prefer drop-and-replay over in-place
migration." In Rust that costs a recompile and redeploy. In cljrs it is
editing an EDN map and a `case` branch, then `(r/rebuild! rt)`. The `.jsonl`
tape is the only thing with a stability contract; everything else is
disposable. This is the property that makes small apps *flourish* — the cost
of changing your mind approaches zero.

**5. A performance ramp exists when it matters.**
The tree walker is plenty: reducer throughput is bounded by the append fsync,
not by interpretation. But both cljrs implementations have a tiering story
(`defn-native` / Cranelift JIT), so a hot reducer or a heavy query predicate
can be lowered without leaving the language. Fan-out loops in the microblog
example below are the realistic first candidates.

## Why `.jsonl` beats `.sqlite` as the source of truth

The temptation is "just use sqlite for the log." Resist it:

- **The tape is append-only; sqlite is a mutable B-tree.** A JSONL file's
  *format* enforces the discipline the architecture depends on. There is no
  UPDATE statement to abuse at 2am.
- **Greppable, diffable, streamable.** `tail -f log.jsonl`, `jq`, `git`,
  `rsync --append` all work. Recovery tooling is `less`.
- **One fsync per group commit is the whole write path.** durable already
  does group commit (`append_batch`: N events, one `sync_data`). sqlite adds
  a WAL, a schema, and a query planner to a thing that needs none of them.
- **The projection already has an indexed store.** RocksDB holds the indexed,
  precisely-updatable state. Putting sqlite under the log would mean two
  databases and zero flat files; jsonl + RocksDB means one database, and the
  one copy of the truth is human-readable.

sqlite's *virtue* — embedded, single-file, zero-ops — is the design target of
ramalite as a whole, not of its log format.

## The ramalite surface

A module is one EDN schema, one reducer, one open runtime:

```clojure
(def module
  {:schema  {...}                       ; shapes: leaf / map-of / list-of / deque-of / sum
   :reduce  (fn [tx meta event] [...])  ; pure: returns a vector of reified writes
   :log     "app.jsonl"
   :proj    "app.db"})

(def rt (r/open! module))
(r/append! rt {:type :something ...})   ; stamp → fsync → reduce → commit
(r/one rt [:users "alice" :name])       ; Nav algebra, EDN spelling
(r/rebuild! rt)                         ; drop projection, replay tape
(r/verify! rt)                          ; incremental == replay-from-zero
```

The Rust host exposes exactly six things through opaque handles:
`open!`, `append!` (and `append-batch!`), the query terminals
(`one`/`select`/`subtree`/`entries`/`project`/`explain`), a read primitive
for reducers (`peek`, backed by `Tx::db` — committed state only), `rebuild!`,
and `verify!`. Everything else — write constructors, path spelling, the whole
application — is Clojure data.

EDN → engine mapping:

| cljrs | durable |
|-------|---------|
| `:field` keyword in a path | `Nav::Field` |
| string / number / vector literal in a path | `Nav::Key` / `Nav::Index` |
| `r/ALL`, `r/KEYS`, `r/VALS`, `r/ENTRIES` | `Nav::All` / `Keys` / `Values` / `Entries` |
| `(r/where pred)`, `r/FIRST`, `r/LAST`, `(r/slice a b)` | `Nav::Where` / `First` / `Last` / `Slice` |
| `(r/gt :epoch 4)`, `(r/and ...)`, `(r/exists [...])` | `Predicate` / `Expr` |
| `(r/put p v)` `(r/del p)` `(r/add p n)` `(r/push p v)` `(r/clear p)` | reified `Write` ops |

`explain` keeps its honesty guarantee: the REPL prints `POINT` / `BOUNDED` /
`SCAN`, so a prefix scan cannot pretend to be a point get even when it's one
line of EDN.

## The UI layer: `(server ...)` / `(client ...)` blocks

The strongest version of ramalite is not a database library with a REPL — it
is the full-stack pattern demonstrated by
[borkdude/buzz](https://github.com/borkdude/buzz) and
[evaleval](https://github.com/sortersocial/todo-tournament/blob/main/contestants/clojure-evaleval/src/evaleval/core.clj):
one file, one language, and marks that tell the runtime which side of the
wire an expression runs on.

**How those two work.** In buzz, a `defui` body is client code; `(server
expr)` is a value computed on the server and streamed to the browser,
re-computed whenever a watched atom changes; `(server! expr)` is an RPC;
`(client expr)` carries a browser value into a `server!` form; `local-state`
is per-browser. Squint compiles the UI to JS — no ClojureScript toolchain, no
Node. In evaleval, a `(server ...)` block is *serialized as code* into a
signed hidden input and eval'd when the form posts — code-as-data crossing
the wire, with an HMAC because the wire format is `eval`.

Both prove the ergonomics. Both also have the same two structural gaps, and
they are exactly the two things durable is:

**1. Their server state is `(defonce clicks (atom 0))`.** Ephemeral, no
history, gone on restart, unwatchable at any granularity finer than the whole
atom. Put ramalite underneath and the marks acquire precise meanings:

- `(server! expr)` → **an event append**. Every button click is a line on
  the tape: fsynced, stamped, replayable, auditable.
- `(server expr)` → **a query over the projection**, re-run when the data it
  reads changes.
- `local-state` stays in the browser, exactly as in buzz.

State now survives restarts (buzz already reconnects browsers after a server
restart — combined, the page comes back *with its data*). And you can edit
the reducer while browsers are connected, `rebuild!`, and every open page
re-renders into the re-scored world.

**2. Their reactivity is coarse or manual.** Buzz watches whole atoms: any
change re-renders every mount that watches it. Rama's answer is reactive
PState queries — subscribe to a path, receive fine-grained diffs. durable can
have that *mechanically*, because both sides of the dependency are already
data: an event's commit is a batch of reified `Op`s, each carrying its
RocksDB key; a mounted `(server ...)` query has an `explain`-able key range
(`POINT` / `BOUNDED` / `SCAN`). Invalidation is key-range intersection:

```text
append → reduce → commit {write keys} → ∩ {subscribed query ranges}
       → re-run only the hit queries → patch only those browsers
```

No dependency tracking framework, no dirty flags — the write set and the
read set are byte prefixes, and prefix overlap is a comparison. This fills
the one row of the Rama table durable was missing: reactive queries.

**3. The security boundary comes for free.** evaleval must sign its snippets
because its wire format is arbitrary code. ramalite's wire format is already
a closed algebra: a browser can *append a recognized event* (the reducer
decides what it means) and *run navigation data* (no callables, by
construction). The client/server split lands exactly on the line durable
already drew for its Python clients: appenders and queriers, never mutators.

The composed programming model, in one component:

```clojure
(defui scoreboard []
  (let [scores (server (r/entries rt [:scores r/ENTRIES]))   ; subscribed range
        step   (local-state 1)]                              ; browser-only
    [:div
     (for [[player n] (sort-by (comp - val) scores)]
       [:p player ": " n])
     [:button {:on-click (fn [_]
                           (server!                          ; event, on tape
                            (r/append! rt {:type :points
                                           :player "alice"
                                           :delta (client @step)})))}
      "add"]]))
```

One file holds the schema, the reducer, the component, and the server. The
tape holds everything that ever happened to it.

## Example applications

Three apps in [`../examples/ramalite/`](../examples/ramalite/), written in
cljrs against the surface above:

- [`leaderboard.cljrs`](../examples/ramalite/leaderboard.cljrs) — the README
  example, ported. Blind `Sum` merges, one leaf, four events.
- [`microblog.cljrs`](../examples/ramalite/microblog.cljrs) — Rama's flagship
  demo shape at sqlite scale: follows, posts, fan-out-on-write timelines.
  Shows a reducer *reading* committed state (`peek`) to drive fan-out.
- [`ranking.cljrs`](../examples/ramalite/ranking.cljrs) — pairwise votes into
  a `Sum<f64>` edge graph with per-scope isolation and a bounded
  recent-votes deque. Shows `transform_values`-style decay as an event.
- [`todo-ui.cljrs`](../examples/ramalite/todo-ui.cljrs) — the full-stack
  pattern: schema, reducer, `defui` with `(server ...)`/`(client ...)`
  marks, and the HTTP server in one file. Shows key-range invalidation
  driving reactive re-renders.

## What ramalite is not (inherited honestly)

One writer process. Not distributed. No query topologies spanning
partitions — there are no partitions. Map iteration is byte order. If you
outgrow it, the tape is portable: replay your `.jsonl` into actual Rama.
